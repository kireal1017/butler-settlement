### 잡은 함정 3개 — 키를 넣어도 안 되던 이유

1. **K-apt 경로가 폐기돼 있었습니다.** 코드가 `AptListService3/getTotalAptList3` 를
   불렀는데 현재는 **V4** 입니다. 폐기된 경로는 `NO_OPENAPI_SERVICE_ERROR(400)` 를 내는데,
   **이 검사가 키 검사보다 먼저**라 키를 쓰레기로 바꿔도 같은 에러가 납니다.
   그래서 "키가 틀렸다" 로 오진하기 쉽습니다.
2. **`callApi` 가 상태코드만 보고 던져 원인을 지우고 있었습니다.** `K-apt API 400` 만
   남고 본문의 `returnAuthMsg` 가 버려졌습니다. 본문을 먼저 읽도록 고쳤습니다.
3. **CLOVA 엔드포인트가 비공개 InvokeURL 이었습니다.** 도메인에 할당되는
   `clovaocr-api-kr.ncloud.com/external/v1/…` 는 공식 문서가 "보안을 위해 외부 서비스에
   바로 공개되지 않는다" 고 명시한 주소로, 사설 IP(`10.223.x`)로 풀려 타임아웃만 납니다.
   **API Gateway 자동 연동** 후 나오는 `…apigw.ntruss.com/custom/v1/<도메인ID>/<키>/general`
   을 써야 합니다. General OCR 의 URI 가 `POST /general` 이라 **끝의 `/general` 이 필수**입니다.

> 인증키는 **계정당 1개**입니다. API 마다 키가 따로 나오지 않고, 활용신청만 API 별입니다.
> K-apt 는 서비스가 셋(목록·장기수선충당금·기본정보)으로 나뉘어 있어,
> 하나만 신청하면 나머지는 403(등록되지 않은 서비스키)이 납니다.

## 실데이터 적재 (2026-09-22) ✅

키를 넣어도 정산 숫자가 바뀌지 않던 이유는 **적재 경로가 통째로 없었기** 때문입니다.
`fetchLtrfRates()` 를 아무도 호출하지 않았고, 실 API 결과를 `ltrf_rates` 에 넣는 코드가
존재하지 않았습니다. 이번에 그 계층을 만들었습니다.

### 설계 판단

**① 환산 공식 — `sLevy ÷ privArea`**
K-apt 가 주는 `sLevy` 는 단지 전체 월 부과"총액"입니다. 엔진은 원/㎡ 단가에 세대
전용면적을 곱하므로, 분모도 **전용면적합(`privArea`)** 이어야 단위가 맞습니다.
그동안 "총 전용면적을 K-apt 가 주지 않는다"고 적혀 있었으나, 기본 정보제공 서비스의
`privArea` 가 정확히 그 값입니다.

**② 네트워크는 `calculate()` 바깥에서 끝냅니다.**
`calculate()` 를 async 로 바꾸지 않고 `ensureRates()` 를 라우트가 먼저 부릅니다.
엔진 입력을 만드는 경로가 동기 함수로 남아야 확정된 정산서를 나중에 그대로 재계산해
검증할 수 있습니다 (절대 규칙 1의 연장).

**③ 결측 월만 채우고, 미공개 구간은 묻지 않습니다.**
전 구간을 매번 받으면 호출 한도를 금방 쓰고 확정된 근거가 흔들립니다.
K-apt 는 공개가 한 달가량 늦으므로 이번 달·미래는 요청 자체를 하지 않습니다 —
막지 않으면 퇴거예정일이 미래인 계약은 미리보기를 열 때마다 헛호출이 쌓입니다.

**④ 한 단지 안에서 실 단가와 시드 단가를 섞지 않습니다.**
처음엔 시드를 남겨 뒀더니 실측 235.97원/㎡ 옆에 시드 554.6원/㎡ 이 끼어 그 달만
금액이 두 배로 뛰었습니다. 화면에는 둘 다 그냥 "단가"로 보여 설명할 수 없습니다.
적재에 성공하면 그 단지의 시드 단가를 지우고, 빠진 달은 엔진이 직전 실단가를
이어 쓰며 `imputed` 로 표시합니다. **추정했다는 사실이 보이는 편이 낫습니다.**

**⑤ 단지 검색은 로컬 테이블만 봅니다.**
목록 API(V4)에는 단지명 검색 파라미터가 없고 전국 목록을 페이지로만 줍니다.
매 검색마다 실 API 를 때리면 찾는 단지가 그 페이지에 없어 0건이 나옵니다.
`sync-list` 로 한 번 받아 두고 그 위에서 검색합니다 — 로컬이지만 내용은 실데이터입니다.
덤으로 "실 검색 결과에는 로컬 `id` 가 없어 집 추가가 400" 이던 문제도 사라졌습니다.

**⑥ 시드 단지를 실재하는 단지로 바꿨습니다.**
가짜 단지코드로는 키를 넣어도 동기화가 아무것도 못 받아 실연동을 보여줄 수 없습니다.
시드 단가(`ltrfBase`)도 실제 부과액에 맞춰 두어, 실 단가로 갈아끼워도 금액이 크게
튀지 않습니다.

### 남은 것

  없앨 수 있습니다 (지금은 호출 1회라 두었습니다).
### 호출 제한 — 원인 규명 (2026-09-22)

"47개월을 연달아 받으면 중간부터 빈 응답(46 → 36 → 0건)" 의 원인을 실측으로 찾았습니다.
일일 한도가 아니라 **초당 요청제한**입니다 — HTTP 429 · `resultCode 23`.

| 실험 | 결과 |
|---|---|
| 목록 API 1,000건 × 5페이지 연속 | 전부 `code=00`, ~500ms/건 |
| 월부과액 API 20회 연속 (간격 0) | 실패 0건 |
| 그 직후 20회 | **20건 전부 429** |
| 회복 — 5초 간격 단발 호출 | 25초까지 429, **30초에 회복** |
| 회복 후 12회 (간격 300·600·1000ms) | 각각 실패 0건 |

**조치**: `fetchLtrfRates` 가 한 번에 **20개월까지만**, 300ms 간격으로 받고,
429 를 만나면 즉시 중단합니다. 계속 두드리면 전부 429 가 되어 성공할 수 있었던
달까지 잃습니다. 남은 달은 다음 조회에서 이어 받고, 그동안 엔진이 직전 단가를
이어 쓰며 `imputed` 로 표시합니다.

**전국 목록 동기화는 안전합니다.** 22,322건을 받아도 호출은 **23회**뿐이고
(일일 한도 5,000건의 0.5%), 페이지당 0.5초 응답이 그 자체로 속도 조절이 됩니다.
이용허락범위도 "제한 없음" 이고, 목록 API 는 검색 파라미터가 없어 **페이징이 유일한
조회 수단**이라 전체 조회가 곧 의도된 사용법입니다. 단, 사용자 동작마다 부르지 않고
한 번 받아 두고 씁니다.

### 설계 판단

**① 임대인 화면에서 임차인 역할을 없앴습니다.**
v1 은 한 화면에서 당사자를 바꿔 가며 양쪽을 흉내 냈습니다. 임대인이 임차인 동의를
대신 누를 수 있으면 합의 기록이 증거로서 의미를 잃습니다. 임차인의 응답은
`/share/:token/settlement-response` 로만 들어오고, 임대인 쪽 라우트는 `party` 를
아예 받지 않습니다 (항상 `landlord`).

**② 발행 = 임대인의 제안이자 동의.**
임대인이 자기가 만든 정산서에 다시 "동의" 를 누르는 것은 위 흉내의 흔적입니다.
`issue()` 가 전 항목을 `landlord_status='agreed'` 로 넣습니다. 이의가 오면 고쳐서
다시 발행합니다 — 계약의 거부→수정→재전송 루프와 같은 모양입니다.

**③ 이의에는 사유가 필수입니다.** 없으면 임대인이 무엇을 고쳐야 할지 모릅니다.

**④ 재발행하면 그 계약의 정산 링크를 전부 지웁니다 — 제출을 마친 것까지.**
처음엔 미완료 링크만 지웠더니, 제출까지 끝낸 옛 링크가 살아남아 새 정산서를
열어 줬습니다. 화면에는 "확인이 제출되었습니다" 라면서 **바뀐 금액**이 보이는
상태가 됩니다. 링크가 계약에만 매여 있고 정산서 id 를 들고 있지 않아서 생기는
일이고, 옛 정산서는 이미 지워졌으니 그 응답 기록도 남아 있지 않습니다.

**⑤ 임차인에게 `landlord_note` 를 보내지 않습니다.** 임대인의 내부 메모입니다
(테스트로 고정).

### 브라우저 검증 — 합의 한 바퀴

계약 ④ 이지은으로 두 탭을 띄워 돌렸습니다 (임대인 `/contracts/4/settlement`,
임차인 `/t/:token`).

1. 발행 → 임차인 동의 0/4, **당사자 전환 토글 없음**
2. 확인 링크 발급 → `http://localhost:5173/t/…` 노출 · 복사 버튼
3. 임차인 탭: 임대인 크롬 없음, 최종 반환액 451,761,278원, 항목 4건
4. 3건 동의 + 1건 이의(사유 입력) → `4/4 확인함` → 제출 → 링크 잠김
5. 임대인 화면: **임차인 동의 3/4 · 이의 1건**, "임차인이 확인을 마쳤습니다 (시각)",
   확정 버튼 비활성, 항목을 펼치면 이의 사유 표시

**① 소유자 추출을 스펙 정규식에서 바꿨습니다**

V2-SPEC §4.2 의 `(?:소유자|공유자)\s*([가-힣]{2,5})` 를 그대로 쓰면 **공유자 케이스에서 깨집니다.**
공유자 등기는 '공유자' 다음에 이름이 아니라 `지분 2분의 1` 이 먼저 와서 "지분"이 이름으로 잡힙니다.

대신 **"마스킹된 등록번호 바로 앞의 한글 덩어리"** 를 이름으로 읽습니다.
등록번호는 단독·공유 어느 표기에서나 이름 뒤에 붙으므로 훨씬 안정적입니다.

여기에 §4.2 의 "순위번호가 가장 큰 소유권 등기" 규칙을 더해,
**갑구의 마지막 소유권보존/이전 항목 이후 구간에서만** 이름을 찾습니다. 그래서
앞순위 소유권보존의 시행사(주식회사대한건설)가 현재 소유자로 잡히지 않습니다.
`소유권이전청구권가등기` 는 소유자 등기가 아니므로 제외합니다.

`uploads/registry/` 안인지 확인하고 스트리밍합니다. 경로를 입력받지 않으므로 경로 조작이
불가능합니다. 저장 파일명도 원본 이름을 쓰지 않고 `<난수>__정제된이름` 으로 바꿉니다.

### 설계 판단

**① 계약은 이미 등록된 집에 붙습니다**

v1 의 `POST /contracts` 는 호출할 때마다 `units` 행을 새로 만들었습니다. v2 는 집이
CRM 의 1급 개체이므로 `unitId` 를 받아 붙이기만 합니다. 집 생성은 `POST /units` 담당입니다.

**② 품목 시공 이력을 계약 작성 화면이 자동으로 물어옵니다**

`/contracts/new?unitId=` 진입 시 `GET /units/:id` 의 `items`(품목별 최신 시공일)를 읽어
`rule_items` 를 미리 채우고 **이력 승계** 배지를 답니다.
**이것이 §1 의 "고리가 닫히는 지점"** 입니다 — House Log 가 10년 뒤 매도용 기록이 아니라
2년 뒤 다음 계약의 입력값이 되는 부분.

**③ 임차인 확정 버튼을 임대인 화면에서 뺐습니다**

§0 은 임차인이 **공유 링크로 전체 동의 / 거부(사유)** 를 하도록 정했습니다.
임대인 화면에 '임차인 확정' 버튼이 남아 있으면 임대인이 임차인 동의를 대신 누를 수 있어
Rule Lock 의 의미가 사라집니다. 5단계에서 토큰 화면이 이 자리를 채웁니다.

**④ 재발송하면 이전 링크를 버립니다**

살아 있는 확인 링크가 둘이면 어느 응답이 유효한지 알 수 없습니다.
`sendContractLink()` 가 미완료 `contract_review` 링크를 지우고 새로 발급합니다.

### 설계 판단

**① 임차인 화면은 임대인 크롬을 노출하지 않습니다**

헤더의 임대인 이름·전환 버튼·K-apt 배지를 `/t/` 경로에서 숨기고, 로고도 링크가 아닌

**② 같은 숫자를 임차인 언어로 다시 씁니다**

임대인 화면은 `임대인 부담`, 임차인 화면은 `내가 대신 낸 금액은 퇴거 때 돌려받습니다`.
숫자와 규칙은 같고 표현만 다릅니다. 가설 2("양 당사자가 같은 숫자를 보고 합의에 도달하는가")가
성립하려면 임차인이 그 숫자의 의미를 이해해야 합니다.

**③ 규칙 저장 로직을 라우트에서 service 로 옮겼습니다**

`PUT /contracts/:id/rules` 가 라우트 안에서 SQL 을 직접 돌리고 있었습니다.
CLAUDE.md 계층 규칙 위반이기도 하고, 아래 버그를 고치려면 트랜잭션이 필요했습니다.

### 잡은 버그 2개 — 둘 다 거부 루프에서만 터집니다

**(1) `FOREIGN KEY constraint failed` — 거부된 규칙을 고칠 수 없었습니다**

기존 `PUT /rules` 는 저장할 때마다 이전 `rule_sets` 행을 **삭제**하고 다시 넣었습니다.
그런데 임차인의 거부 기록(`contract_responses.rule_set_id`)이 그 행을 참조하고 있어
거부 직후 규칙을 고치면 저장이 실패했습니다. **거부 → 수정 → 재전송 루프 전체가 막힌 상태.**

`saveRuleSet()` 이 **참조 여부를 보고 갈라지도록** 고쳤습니다.

| 상황 | 동작 |
|---|---|
| 응답·정산서가 참조 중 | 새 버전 생성 (v1 보존) |
| 아무도 참조 안 함 (작성 중 반복 저장) | 같은 버전 덮어쓰기 |

"임차인이 v1 을 거부했다" 는 기록은 v1 이 남아 있어야 말이 됩니다.

**(2) 새 제안을 열었는데 이전 거부가 표시되고 동의 버튼이 사라졌습니다**

임차인 화면이 응답 완료 여부를 **계약의 최신 응답**으로 판단했습니다.
거부 후 임대인이 고쳐 보낸 새 링크를 열면 이전 버전에 대한 거부 기록이 잡혀
"수정 요청함" 으로 보이고 동의할 수 없었습니다. 판단 기준을 **이 링크의 `completedAt`** 으로
바꿨습니다.

### 브라우저 검증 — 루프 전체를 클릭으로 확인

1. 임차인 링크 열람 → 계약·규칙·품목 확인 → **수정 요청** (사유 입력)
2. 임대인 계약 상세에 **"임차인이 수정을 요청했습니다"** + 사유 그대로 도착
3. 임대인이 선수관리비를 `소유자 납부` 로 수정 → 저장 (**v2 생성**)
4. 임대인 재확정 → **재발송** (새 토큰, 이전 링크 폐기)
5. 임차인이 새 링크에서 **전체 동의** → "계약이 성립되었습니다"

최종 DB 상태:

```
계약 5 · 정하늘   status=active    집 305동 703호 vacancy=occupied
rule_sets   v1(거부, 임대인만 서명)  v2(동의, 양측 서명)
responses   v1 → rejected            v2 → accepted
share_links 2개 모두 completed
```

거부와 동의가 **각자 본 버전에 붙어 있습니다.** 나중에 분쟁이 생겨도
"누가 어느 버전에 무엇을 했는지" 가 남습니다.

### 테스트 13건이 잡는 것

- 토큰은 자기 계약만 연다 (**§10 체크리스트**) · 없는 토큰 404 · 만료 링크 410
- 첫 열람 시각 기록 · 거부 사유 필수 · 잘못된 decision 거절
- 동의 → `active` + `occupied` + 임차인 서명
- 같은 링크로 두 번 응답 불가
- **거부된 규칙을 고치면 새 버전이 생기고 v1 이 보존된다** (위 버그 (1) 회귀 방지)
- 참조 없는 규칙은 같은 버전에 덮어쓴다 (작성 중 버전 폭증 방지)
- 재전송 시 살아 있는 링크는 하나
- 규칙 없음 / 임대인 미확정 발송 차단

> DB 가 필요한 첫 테스트라 `DB_PATH` 를 임시 파일로 지정하고 동적 import 합니다.
> 엔진 테스트는 여전히 DB 를 모릅니다.

**① 크론을 두지 않았습니다.** 홈을 열 때 `refreshTasks(landlordId)` 가 현재 DB 상태에서
"지금 떠 있어야 하는 할 일 집합"을 계산하고 테이블을 그 집합에 맞춥니다 (V2-SPEC §3 그대로).
데모에서 결정적으로 재현되고, 시간을 앞으로 돌려 놓고 기다릴 필요가 없습니다.

**② 조건이 사라진 할 일은 `done` 이 아니라 삭제합니다.**
`done_at` 을 찍어 남겨 두면 같은 조건이 다시 성립했을 때 유일 인덱스
(`idx_tasks_contract_kind`) 에 걸려 새로 만들지 못합니다. 갱신 결정을 했다가 되돌리는
경우가 실제로 있어서, 테스트로 고정해 뒀습니다.
대신 이미 떠 있는 할 일은 문구만 갱신하고 `created_at` 을 보존합니다 — "며칠 전부터
떠 있었는지"가 남습니다.

**③ 갱신 할 일 두 종류가 겹치지 않게 했습니다.**
스펙의 조건을 문자 그대로 쓰면 `renewal_decision`(D-180 이내)과
`renewal_deadline`(D-60 이내)이 만료 60일 전부터 **동시에** 뜹니다. 같은 계약에 같은
용건이 두 줄 뜨는 것은 잡음이라, 통지 기한이 남아 있는 동안은 `renewal_decision`,
기한 당일·이후는 `renewal_deadline` 으로 넘어가게 분할했습니다. 날짜 경계값은 그대로입니다.

**④ 날짜 판단은 전부 `timeline.js` 를 거칩니다.** 홈 카드와 할 일이 다른 계산을 하면
"카드는 D-60 이라는데 할 일은 안 뜬다"가 됩니다. 2단계에서 타임라인을 단일 원천으로
만들어 둔 것이 여기서 값을 했습니다.

**⑤ severity 는 "놓치면 되돌릴 수 있는가"로 정했습니다.**
`urgent` = 지나면 법적 효과가 확정됨(묵시적 갱신) · `warn` = 일정이 밀리거나 상대가
기다림 · `info` = 알고만 있으면 되는 것. 팔레트는 pink / ochre / teal 로 나눠
같은 색이 나란히 오지 않게 했습니다.

### 설계 판단

**① 입주일을 새로 잡지 않습니다. 이것이 이 단계의 핵심입니다.**

**② "이번 갱신 기간의 시작일"을 컬럼으로 두지 않았습니다.**

**정산 없이 닫히는 유일한 경로**입니다 (거주가 이어지므로 보증금을 돌려주지 않습니다).

**④ 갱신 발송 중에는 집을 '계약 진행 중'으로 되돌리지 않습니다.**

**⑤ `decline-renewal` 을 추가했습니다** (스펙에 없는 경로).
갱신하지 않기로 한 것도 **결정**이라 기록해야 할 일이 해제됩니다. 계약을 끝내지는 않습니다 —
임차인은 만료일까지 거주하고, 퇴거 절차는 8단계에서 따로 시작합니다.

**① 귀책 0%(통상손모)도 항목으로 남깁니다.**
공제액이 0이니 빼도 계산은 같습니다. 그런데 빼면 임차인이 정산서를 보고
"욕실 수전은 왜 아예 없지?" 를 묻게 되고, 그 질문이 합의를 늦춥니다.
**"봤고, 임대인 부담으로 판단했다"** 가 기록으로 남는 것이 이 서비스의 값입니다.

**② 검토는 통째로 덮어씁니다 — 단, 이 점검이 만든 항목만.**
`reviewInspection` 은 `damage_reports WHERE inspection_id = ?` 만 지우고 다시 넣습니다.
손으로 추가한 항목(`inspection_id IS NULL`)은 건드리지 않습니다.
화면에서 행을 지웠다 다시 만드는 편집 방식과 맞고, 다시 검토해도 중복이 쌓이지 않습니다.

**③ 검사에 걸리면 아무것도 저장하지 않습니다.**
항목 검증을 트랜잭션 **밖에서** 먼저 전부 돌립니다. 다섯 항목 중 네 번째가 잘못됐을 때
앞의 세 개만 들어가면 화면과 DB 가 어긋납니다. 테스트로 고정했습니다.

**④ 점검은 계약당 하나. 재요청은 "다시 열기" 입니다.**
처음에는 재요청이 링크만 새로 냈는데, 그러면 이미 제출한 임차인이 사진을 더 올릴 수
없었습니다(브라우저에서 발견). 지금은 재요청이 상태를 `requested` 로 되돌리고
**사진과 검토 결과는 그대로 둡니다.** 다시 검토하면 항목이 갈아끼워집니다.

**⑤ 임차인에게는 사진만 갑니다.**
점검 링크 응답에 `damage_reports` 를 넣지 않습니다. 임대인이 매긴 귀책비율은
정산서에서 **항목별 계산 근거와 함께** 보여줄 것이고, 맥락 없이 숫자만 먼저 보이면
불필요한 다툼이 됩니다. 파일 경로도 내보내지 않습니다 (테스트로 고정).

**⑥ "퇴거 절차 시작" 은 만료에 따른 종료 절차입니다.** 파기가 아닙니다.
퇴거일 기본값은 만료일이고 협의로 조정합니다. 이 날짜가 정산 계산의 전제이자

## 2026-09-23 · 확정한 집이 공실로 돌아오지 않던 문제

집 상태 전이에 **돌아오는 길이 없었습니다.**
